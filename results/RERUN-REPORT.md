# RERUN — the re-measurement report

**What this is.** Three audit rounds read the artifacts in `results/`. None re-measured
anything. This is the re-measurement: every probe in `README.md`'s three-tier table was
re-run against the code, the sidecar and the APIs that are in the tree *today*, and every
regenerated artifact was compared leaf-by-leaf against an immutable byte-copy of the
published one.

**The question it answers.** Are the published artifacts reproducible?

**The answer, in one line.** The deterministic local probes reproduce **bit-for-bit**. The
paid LLM arms reproduce **within the noise their own scripts warn about**. **Five artifacts
do not reproduce at all, and in every one of those five the cause is that the artifact was
produced by code the tree no longer runs** — not that the measurement failed.

---

## 0. How to read this, and what "re-measured" means

Nothing here is an inference from a diff of a file against itself. That failure mode
actually occurred during this exercise: an early comparison harness diffed each artifact
against `results/_superseded/<name>.pre-rerun`, and for ten artifacts the "pre-rerun" copy
was a byte-copy of the artifact (the archiver copies *before* the run; when the run then
failed, backup == artifact). That harness reported ten clean reproductions for artifacts
that had never been re-run. It was caught and the ten were re-run for real.

Every row below therefore states one of:

| label | meaning |
|---|---|
| **RE-MEASURED — BIT-FOR-BIT** | the artifact's bytes were regenerated by its own script and every leaf matches except run state (call counter, uptime, wall-clock timestamp) |
| **RE-MEASURED — WITHIN NOISE** | regenerated; the headline point estimates match, per-item values do not (an unpinned stochastic arm) |
| **RE-MEASURED — DIFFERENT CONDITION** | regenerated; the *input* differs, so the two runs are not two runs of the same experiment |
| **RE-MEASURED — DID NOT REPRODUCE** | regenerated from the same nominal input; the numbers moved |
| **NOT RE-RUN** | bytes unchanged from the published artifact; no claim either way |

**Integrity controls used throughout**

- `rerun/baseline/` — a byte-copy of all 53 files in `results/` taken before anything was
  touched, with `rerun/baseline.MANIFEST.sha256`. Every comparison is against this, never
  against a backup of the file being tested.
- `rerun/archive_before_rerun.py` — copies `results/<name>` to
  `results/_superseded/<name>.pre-rerun` before any script may rewrite it, and appends the
  reason to `results/_superseded/README.md` (task constraint 3).
- **The sidecar on 8787 was never restarted, reconfigured or killed.** It went from 3,505
  to 5,289 calls during this work with **0 failures**.
- **No credential value was written to any file.** The only credential-adjacent output is
  the name of a ref, and a boolean that no value is stored.
- Tier-2 sweeps that launch their own servers (P17, P18) were run from a scratch copy of
  the repo, `D:\Projects\llm-jev-laya-bench-rerun-scratch`, so they wrote nothing into the
  published `results/`.

**One interpreter trap, for the reader who follows.** The Tier-1 scripts run on a bare
Python 3.12. The Tier-2 probes do **not**: any probe that calls `client.count_tokens()`
needs the `tokenizers` package and fails with
`SidecarError: the 'tokenizers' package is required for protocol-correct budget accounting`
under a bare interpreter. This first pass failed 7 of 13 local batteries that way. They were
re-run under `LAYA_VENV_PYTHON` (`D:\Projects\laya-family\.venv-laya`), which is what
`bench_env.py` names for this purpose — but `README.md` never says to use it for the probes,
only that it is "the interpreter that can import `laya_mcp`". The failed runs were **not**
counted as non-reproductions.

### 2.2 The `instrument_hashes()` schema change

Eight of the artifacts above differ **only** in their provenance block: the published ones
carry four flat keys (`capability.py`, `planning.py`, `server.py`, `worker.py`), while
`laya_client.instrument_hashes()` today returns `snapshot.*` and `worktree.*` keys plus a
`drift` block. `laya_client.py` changed mid-campaign.

Consequence, and it generalises: **re-running an early artifact under current code cannot
reproduce its provenance block even when every measurement reproduces.** The measurement and
the metadata about the measurement have different lifetimes, and the tree keeps only one copy
of each.

The `drift` block also records something no document states: the live worktree has drifted
from the pinned snapshot in **three modules** — `cli.py`
(`B9515084…` snapshot vs `9A568C0C…` worktree), `mcp_server.py` (`C13E5152…` vs
`717CEB9F…`) and `__init__.py` (`8DF1783C…` vs `47AD02DA…`). The snapshot was frozen at
10:20:01Z and those files were rewritten at 10:22:13/10:22:28/10:25:42 local — minutes
*after* the freeze. Fourteen of the seventeen modules match; these three do not. Every
backfilled `drift` block now records it, and nothing reads it.

### 3.3 `P22b`: the deterministic judge moved, so the input moved

Laya is **deterministic**: six identical requests returned byte-identical answers for both
the `noul` and the `choice` primitive (`rerun/laya_determinism.py`). So when a Laya arm
moves, the input moved.

For `P22b-fixed-r1`, per item, against the published draw:

| check | result |
|---|---|
| item ids | 68 / 68 in common |
| `truth` differs | **0 / 68** |
| `state_tokens_laya` differs | **0 / 68** |
| **`laya_value` differs** | **56 / 68** |
| `laya_correct` differs | 33 / 68 |
| `llm_correct` differs | 24 / 68 |

Same states, same truths, same token counts — different **option sets**. And the cause is in
the tree: `p22_chain_audit.py:281` calls `build_items()` with the defaults
(`legacy_options=False`), while `p22f_repair_denominator.py:200` reconstructs the **published**
`P22b` battery with `build_items(legacy_options=True)`. The published draws were made with
the pre-round-5 option construction; the generator now uses the new one. Nothing can select
the old one from the generator's own entry point.

The published regime-3 numbers therefore cannot be re-measured, only re-derived: Laya
per-K accuracy `{0.4167, 0.25, 0.2857, 0.2609}` (all three published draws) versus
`{0.25, 0.3333, 0.3333, 0.2174}` (all three re-run draws — identical to each other, because
Laya is deterministic and the input is now fixed). Δ_catch: published `−0.2332 / −0.2473 /
−0.1816`; re-run `−0.0556 / −0.0985 / −0.0663`. Still negative, so the paper's negative
claim holds; the magnitudes move by up to 3×.

## 4. Is the idempotency defect real?

**Yes — and it is worse than `ERRATA` §10.3 states, but it is also not a loss.**

Two independent lines of evidence.

**(a) It has already happened, and it is on disk.** `results/P27b-plugin-crossval.json` and
`results/_superseded/P27b-plugin-crossval.json.pre-repair` differ in **exactly two leaves**,
both `latency_self_report_vs_wall_clock._stale_superseded.*`:

| field | pre-repair copy | current artifact |
|---|---|---|
| `superseded_unmatched_p50_ms` | **915.1** | **1191.8** |
| `superseded_ratio_of_medians_unmatched` | **2.02** | **1.55** |

Everything else in those two files is identical — 207 of 209 leaves. So the round-5 `p27f`
pass **repaired nothing**. The derived values were already current in its input; its only
effect was to overwrite the forensic record with the post-repair values. `ERRATA` §7.1
describes a repair that had happened in an *earlier* pass; the round-5 run it attributes the
repair to was a no-op apart from the corruption.

**(b) Re-running it again cannot detect or undo this.** `rerun/p27f_idempotency_test.py`
ran `p27f` three more times on a byte-identical scratch copy. Each pass printed
`unmatched p50_ms : 1191.8 -> 1191.8` — a repair report for a repair that did not happen —
and left `_stale_superseded` at `{1191.8, 1.55}`. The loop is a **fixed point only after the
historical record has already been destroyed**. Because `save()` writes the backup only when
one does not already exist, a second pass can never recover the values it replaced.

**(c) The values are not lost.** `_superseded/P27b-plugin-crossval.json.pre-repair` preserves
`915.1 / 2.02`, and so does `ERRATA` §7.1 and the repair script's own docstring. `ERRATA`
§10.3's "overwrote the historical record" is true of the in-artifact field only; the record
survives one directory away.

**The generalisation, which is the real finding.** Re-running a **generator** destroys every
metadata layer added to the artifact *after* it was measured, because the generator cannot
reproduce it by construction. Observed in three places in this exercise:

- `p29`'s retroactive `_provenance` block — **P21** came back with top-level keys
  `['rows','summary']` and no provenance of any kind, i.e. the re-run re-created precisely
  the defect `ERRATA` §9 existed to fix. **P14** likewise.
- `p27f`'s `_stale_superseded` — gone from `P27b` after regeneration.
- `p27f`'s `cost._ledger_reconciliation` — gone from `P27-jev-live`; in exchange the
  generator now persists the provider-field call's own cost, latency and attempts, which is
  the fix `ERRATA` §7.3 describes.

Nothing in `verify_all.py` notices, because every remaining number is still correct.

**What was done about it.** Not a restore from backup — the backup's block carries the
*published* spend, and re-inserting it would attach stale numbers to freshly measured data.
`rerun/restore_llm_provenance.py` re-adds a block to `P14-llm-arm-full.json` and
`P21-thinking-mode-cost.json` in which **every figure is derived from the artifact it
annotates**, it points at the pre-rerun copy for the original block, and it **skips any
artifact that already carries `_provenance`** so a second pass cannot overwrite its own
record. Derived values: P14 `96` calls, `$0.004757232`, range `[$0.000032634, $0.000102450]`;
P21 `24` calls, `$0.001898700`, range `[$0.000038550, $0.000115950]`.

`paper/05-results-A-draft.md` records a control arm — *"state 79-92 tokens, 6/10, 4/10,
Fisher exact two-sided p = 0.011"* — withdrawn in round 7 because it **has no artifact
anywhere in the tree**, and because its state size coincides with P26's discarded first
prototype.

**It is producible now, and it lands on the withdrawn numbers.**

`rerun/p26_control_low_window.py` imports P26's **own** `build_item` by file path, with the
same seed `20260922` and the same shared-RNG call order, and changes **one** thing: the
filler padding, so the correction sits inside the 512-token window. The padding rule was
fixed before any judgement was read — the smallest `PAD_REPEATS` whose median state is
nearest the withdrawn arm's stated 79-92 tokens. "Padding removed" is `PAD_REPEATS = 0`, and
it gives **exactly 79-92 tokens** (median 85). The range match is a **prediction confirmed,
not a fit**. Filler padding is not drawn from the RNG, so `v0`/`v1` are identical for every
padding value.

**All four numbers reproduce independently.** What this does to the withdrawal:

- The arm's numbers were **real, not invented**.

## 6. What the audits did not find

### 6.1 `results/` mixes measurement with repair layers, and has no room for both

§4's generalisation is the structural version of this. `ERRATA`'s own policy — *"stale fields
are documented rather than silently rewritten"* — is implemented by editing the artifact, so
the documentation and the measurement share a storage slot. Re-running is the operation that
separates them, and it always destroys the documentation. Three instances, one class.

### 6.2 Two `laya_mcp serve` processes are bound to port 8787, with **different loadouts**

| PID | started | command |
|---|---|---|
| 22148 → **22316** | 18:20:34 | `serve --model english --also multilingual --also typed-decisions … --port 8787` |
| 20892 → **7156** | 18:21:00 | `serve --model english --also multilingual … --port 8787` |

`Get-NetTCPConnection` reports the listening socket as owned by **7156** (the two-checkpoint
process), but attribution by CPU-time delta over four queries shows **22316** (the
three-checkpoint process) doing 100% of the work: `+38.7 s`, `+0.156 s`, `+0.031 s`,
`+0.016 s` of CPU, with 7156 at exactly `0.000` every time, and a single monotonic `calls`
counter across eight consecutive `/health` reads.

So the instrument that answered every Laya measurement here — and every published one — is
the **three-checkpoint loadout**, which is the loadout the paper's claims require. Good news.
But two things follow that no document records:

1. **The `checkpoints` field in `/health` is not a loadout record.** It is built from
   `Worker._capabilities` (`protocol/instrument-snapshot/src/laya_mcp/worker.py:434`), which
   `_capability_for()` populates **lazily on first use** (`worker.py:465`). A checkpoint that
   was never launched appears there as soon as something queries it. An artifact that reads
   its loadout from `/health` — as `P3`, `P17` and `P18` all do — **cannot establish its own
   launch loadout**, and the loadout is precisely the variable the README says moves the
   headline number by 2×.
2. A second, idle server bound to the same port is a standing hazard: it is one restart away
   from becoming the instrument, and its loadout is different.

### 6.3 `P17` and `P18` had never been re-run, and one earlier report said they had

Recorded here because it is a *method* finding, not a fact about the artifacts. An early
comparison during this exercise reported `P17` (23 fields) and `P18` (60 fields) as
"REPRODUCED EXACTLY". Both files were byte-identical to their own backups: **they had not
been re-run at all.** A diff against a pre-run backup cannot distinguish "reproduced" from
"never ran" — the check reports success because it cannot see the failure. The detector that
works is the one used here: an artifact may only be called a reproduction if its **bytes
changed** against the immutable baseline. Both were then genuinely re-run and both do
reproduce bit-for-bit (§2), so nothing published is wrong — but the false verdict came
first, and it is the same defect class as `ERRATA` §10.4.

### 6.4 Retrievability of the disputed Jev ratio

`P27b`'s size-matched ratio is printed as 1.94 and now computes to 1.49 while the *unmatched*
ratio has become 1.94. The two figures have swapped places. A careless edit to §5.2 could
leave the text quoting 1.94 while meaning the ratio that is no longer 1.94.

**The five that did not reproduce at all share one cause, and it is not a measurement
failure.** In every case the artifact in `results/` was produced by a version of its script
that the tree no longer contains and cannot reach: `P20`'s rubric fix, `P5`/`P5b`'s item
generator, `P2`'s battery size, and `P22b`'s option construction (`legacy_options=True`,
reachable only from the repair script). **`results/` describes a tree that no longer exists**,
and nothing in `verify_all.py`'s 49 checks can see it, because every individual number is
still internally consistent.

That is the answer to the question this exercise was asked. The instrument is reproducible —
the clamp, the unwindowed gap, the deterministic judge, and the whole of Tier 1 reproduce
bit-for-bit, on the same GPU with the same loadout. The **artifacts are reproducible only for
the code that produced them**, and for five of them that code is gone.
