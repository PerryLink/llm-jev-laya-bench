# §5 结果 A——成本不是约束：三方实测

> 本节的核心动作是**换轴**：论文因此把「谁更便宜」这个问题，替换成「**哪个轴真的把三者分开了**」。

---

## 5.0 为什么这一节需要换轴

**原设想**：证明「判定模型比 LLM 更便宜」。
**实测裁决**：**该主张在算术上无意义** —— 三者的单次成本**都在 10⁻⁵ 美元量级**，而设计里只有 120 个检查点/运行。

| 判定器 | 单次成本 | 120 检查点/运行 |
|---|---|---|
| **Laya**（本地 cuda，自托管） | **边际 ≈ $0**（仅算力） | ≈ $0 |
| **Jev**（openrouter，`typesafe/jev-1.13`） | **$0.0000146 – $0.0002406**（实测 8 档，**随输入 token 单调上升**；设计状态范围内为 **$0.0000146–$0.0000588**） | **$0.0018 – $0.0289**（设计范围内 **$0.0018–$0.0071**） |
| **LLM**（`deepseek-flash`，非思考） | **$0.0000326 – $0.00009645**（**上限取 P14 全部 96 次调用的实测最大值**；$0.0000484 是**均值**，早期版本把它印成了区间的中点，而上限 $0.0000566 **不是任何一批的最大值**——本文自己的 `_provenance` 块早已记录正确的一对） | **$0.0039 – **$0.0116**** |
| **LLM**（`max` 档，最贵） | $0.0001010 | **$0.0121** |

→ **最贵的组合（LLM `max` 档）跑完 120 个检查点约 1.2 美分。**
→ **「省钱」不是一个可辩护的论文主张。** 本节因此**报告成本，但不把成本当作结论**。

## 5.1 成本：实测数字与两个必须同时给出的限定

**LLM 逐 effort 档**（P21，每档 n=6；峰价为低谷 2×，同步记录）：

| effort | 平均 completion token | **平均推理 token** | 平均成本（低谷） | 相对非思考 | p50 延迟 |
|---|---|---|---|---|---|
| **none** | 13.0 | —（字段不存在）| **$0.0000398** | **1.00×** | 720 ms |
| **low** | 70.3 | 57.0 | $0.0000780 | 1.96× | 909 ms |
| **high**（默认） | 84.3 | 71.2 | $0.0000864 | 2.17× | 916 ms |
| **max** | 108.7 | 96.3 | $0.0001010 | **2.54×** | 961 ms |

**限定一：推理 token 计入输出价**，且占输出的 **81–89%**（`max`：96.3/108.7）。
→ **按可见答案计价会严重低估**（V3 的观察在此得到证实）。但**绝对量小**（约 100 token），故倍数有限。

**限定二：峰谷价差恰为 2×**（一手来源：[DeepSeek 价格页](https://api-docs.deepseek.com/quick_start/pricing/)；缓存命中 $0.003 / 未命中 $0.15 / 输出 $0.60 为低谷，高峰为其 2×，高峰时段 UTC 周一至周五 01:00–04:00 与 06:00–10:00）。→ **成本必须标注时段**，只报一档是读者无法审计的选择。

**Jev 的计费差异（重要，且推翻一个早期假设）**：
- **`costUsd: 0` 在 TypeSafe 路线上意为「未报告」，不是「免费」**；
- 本项目实际使用的 **OpenRouter 路线会报告真实 `costUsd`**，且**输出 token 计费**（实测 20 token/次）。
→ **两条路线的计费模型不同，不得混用一张成本表。**

## 5.2 延迟：**这才是把三者分开的轴**

| 判定器 | p50 | 均值 | 最大 | n | 限定 |
|---|---|---|---|---|---|
| **Laya**（本地 cuda） | **37.4 ms**（墙体中位；自报 30.0 ms） | — | **—**（见脚注 4） | 30 | **批大小 1**；**墙体** |
| **LLM**（非思考） | **671 ms** | 699 ms | 1,008 ms | 48 | 直连 API，**客户端墙钟**（`deepseek_client` 以 `perf_counter` 包住 HTTP） |
| **Jev**（openrouter） | **1,192 ms**（n=20，**唯一有产物的一次运行**；合并 n=35 的中位 1,073 ms） | 1,551 ms | 4,019 ms | **20** | **墙体；单次抽样，见脚注 1** |

→ **p50 跨约 25–32 倍**（37.4 ms → 671 ms → ~0.9–1.2 s）。**区间只能取自有产物的数字：下沿 28.7 倍取自合并 n=35 的中位（1,073.4 ms），上沿 31.9 倍取自唯一有产物的那次运行（n=20，p50 1,191.8 ms）**。**⚠️ 早期版本在此写「下沿取自第一次运行、上沿取自第二次」——那两次运行的说法已于第七轮撤回（915.1 ms 是派生字段的修复前取值，不是一次运行），故 24.5 倍一并撤回**：它依赖的 915 ms 只存在于一份**产物未被保留**的早期报告。**方向有利于本地判定器**，但**该轴的单次运行不可复现**（见脚注 1）。

**⚠️ 四点必须同时声明，且第 1 与第 3 点是本轮更正的我方错误**：
1. **⚠️ Jev 的延迟列只有一次有产物的运行；早期版本声称的「两次独立运行」不成立（第七轮撤回）。**
   **事实**：`results\P27-jev-live.json` 记录 **n=20、p50 1,191.8 ms、mean 1,550.6 ms、max 4,018.6 ms**——**这是唯一有产物的 live 运行**。早期版本印的「第一次运行 915 / 1,001 / 1,802 ms」**不是一次运行**：`915.1` 是 `P27b-plugin-crossval.json` 里 `unmatched_direct_for_reference.p50_ms` 的**修复前取值**，而该字段本身就是 P27 `latency.p50_ms` 的一个**副本**；修复重读该副本后它变成 1,191.8。**全树没有任何产物记录过一次 p50 = 915 的 Jev 延迟运行**，且 `_superseded\` 中 P27 的副本其 latency 块与当前**逐位相同**。
   **且「+30% / +55% / +123%」在统计量类型上也不可比**：它们分别把**修复前 p50** 对**修复后 mean**、**单次 max** 对**合并 max** 相减——即使真发生过两次运行，这三个差值也不是运行间极差。
   **能说的**：一次有产物的运行；合并 n=35 的中位 1,073.4 ms（`P27-summary`，**由 n=20 与 n=15 两次不同状态的采集合并**）；以及**一份早期报告记录过 915 ms 而产物未保留该次**——**这是文档缺口，不是已测得的复现性结论**。
   （先前印的 **938.6 ms / 25 倍** 出自合并第一次运行与 `P27c` 的旧汇总；按当前产物重算为 **1,073 ms / 28.7 倍**。两个数都保留在此，**因为它们本身就是这条轴不可复现的证据**。）
2. **三者其实同为客户端墙钟**（Laya 本地计时；LLM 由 `deepseek_client.py` 的 `perf_counter` 包住 HTTP；Jev 由本客户端计时）——论文早期版本把 LLM 一列写成「provider 自报」，**那是错的**。故本阶梯是**同口径**比较。
3. **但这条轴测的主要是网络拓扑，不是判定器的推理开销**：R13 的**未认证 403 拒绝**往返为 **1,011–2,349 ms**，**≥ Jev 的 p50**——即**零推理的往返即可复现整个 Jev 差值**。故正确读法是：**本地 vs 远程**差了约 25 倍（真实且稳定），而**远程 vs 远程**那一截**不是判定器的属性**。
3. **Jev 原印 1,380 ms（n=13），那是插件的自报值。** 第三轮建了独立 HTTP 直连路线，在同一路线、**同尺寸状态**上同时测两者：

| 测量 | n | p50 | min | max |
|---|---|---|---|---|
| 插件自报 `latencyMs`（状态 128 字符） | 7 | **1,851 ms** | 1,233 | 3,141 |
| **本客户端墙体（状态 126 字符，尺寸匹配）** | 5 | **956 ms** | 855 | 2,172 |

⇒ **插件的自报延迟约为独立墙钟的 1.5–1.9 倍**（**同尺寸状态**对比）。**⚠️ 第八轮更正：该比值不是一个稳定数字。** 它是两个**延迟测量**之比，而 §5.2 本身已确立**Jev 的延迟正是那个不复现的量**（同状态、同 n、同成本、同 token 数：p50 1,191.8 → 952.9 ms，−20%；max 4,018.6 → 6,360.4 ms，+58%）。**尺寸匹配的档位是完好的**（两次同为 126 字符 / 347 token / n=5），移动的是**该档自己的 p50：956.2 → 1,244.8 ms**。故正确的表述是 **约 1.5–1.9 倍**：对 `rerun\baseline\P27b-plugin-crossval.json` 为 **1.94**（分母 p50 **956.2 ms**），对 `results\P27b-plugin-crossval.json` 为 **1.49**（分母 p50 **1,244.8 ms**）。**该节的实质发现不受影响**：p50 跨 127× 状态增长基本持平——两次运行方向一致（修复前 +12%，重跑 −10%），**形状复现，只有量级随环境移动 4–33%**。
**⚠️ 三点限制**：(a) 两组**非同批配对**采集（n=7 vs n=5），差距中可能含网络漂移；(b) 论文自己的**未认证 403 拒绝对照**（1,011–2,349 ms，且测于 `api.typesafe.ai` 而非 openrouter）**与插件自报区间（1,233–3,141 ms）重叠**，因此该对照**削弱而非支持**「插件开销」的读法；(c) 故这只记为**待验证旗标**，不是结论。**本表采用墙体值。**
4. **Laya 的 max 留空**：论文早期版本在该格印 **4,864 ms**，但那是 **`P1` 探针（n=18，中位 26.4 ms）**的离群值，**不属于本行的 R13 n=30 序列**（该序列 max 50.5 ms）——**两批样本曾被混列**，已删除。R13 的 n=30 上未测到长尾，故本行 max 留空。
5. 论文更早期版本还印过 **n=23 / p50 1,408 ms / 均值 2,372 ms / 最大 12,055 ms**——这四个数字**全树无出处**，已删除；而 P13 的汇总均值 1,879 ms **算术上不可能**（n=13 时与 min 919／max 11,984 无解，见 `results\ERRATA.md` N-1），**亦已删除**。

→ 这**就是**「本地小判定器」的真实卖点：**不是省钱，是省时间。**

### 5.2.1 Jev 的延迟由**传输**主导——跨 127 倍状态范围基本平坦

**墙体独立测量**（`P27c`，每档 5 次）：

| 状态字符 | 输入 token | **p50** | min | max |
|---|---|---|---|---|
| 126 | 347 | **956 ms** | 855 | 2,172 |
| 7,896 | 1,400 | **881 ms** | 864 | 1,897 |
| 15,999 | 2,495 | **1,073 ms** | 939 | 1,873 |

⇒ **状态放大 127 倍，p50 只从 956 变到 1,073 ms** ⇒ 延迟由**传输**主导，不由状态大小决定。
- **关键对照**：R13 测得的**未认证 403 拒绝**往返为 **1,011–2,349 ms**，与**真实调用同量级** ⇒ **该轴测量的主要是网络拓扑，不是判定器的推理开销**。
→ **论文不得把该延迟写成判定器的固有属性** —— 它随网络位置变化。
→ **协议条款**：报告远程判定器延迟时，必须（a）**注明测量点**（墙体还是自报），（b）附一条**不执行推理的对照往返**（如 403 拒绝），（c）**不要采信被评测方自报的延迟而不做独立测量**——本节的 Jev 一列正是因此被更正了约 2 倍。

### 5.2.2 Laya 的延迟必须带批大小

| 批大小 | 每问摊销 |
|---|---|
| 1 | **30.0 ms**（墙体 37.4 ms） |
| 5 | 6.0 ms |
| 10 | 3.9 ms |
| 20 | **3.2 ms** |

→ **批处理摊销约 9 倍。** 但**双平面回放每个 state 只有一个问题，故批大小被迫为 1** —— 引用 3.2 ms 会**乐观 11.7 倍**（对墙体中位 37.4 ms；若按该表自身的摊销基准 30.0 ms 则为 **9.4 倍**——**两个基准不可混用**，早期版本印的「12 倍」正是把墙体值除以自报批量值得来的）。
→ **强制条款：延迟一律连同批大小与设备一起报告。**

## 5.3 状态窗口：第二个分离轴

| 判定器 | 决定性证据仍可用的最大 state | 失败方式 |
|---|---|---|
| **Laya**（english，三-checkpoint loadout） | **~3,082 字符**（512 token 钳位） | **静默丢弃尾部**；`truncated` 滞后 111 字符 |
| **Jev**（**接入层**窗口） | **≥15,002 字符**（插件）；**直连路线实测接受 39,927 字符** | 容纳，或**告警** |
| **LLM** | 1M 上下文（文档） | 不适用 |

**⚠️ 「16,000 字符上限」已被实测证明是接入层（插件）的，不是 provider 的。**
第三轮建了独立 HTTP 直连路线（`P27`），把状态阶梯推到 **39,927 字符**：

| 状态字符 | 1,965 | 7,959 | 14,952 | 15,951 | 16,395 | 23,943 | **39,927** |
|---|---|---|---|---|---|---|---|
| 输入 token | 598 | 1,408 | 2,353 | 2,488 | 2,548 | 3,568 | **5,728** |
| `noul` | 0.97 | 0.97 | 0.97 | 0.97 | 0.97 | 0.97 | 0.97 |

**证据是 token 记账，不是「无截断」的断言**（这一点必须说清楚）：
- 这条**路线上没有 `truncated` 字段**可查（§6.4.1），且该探测把惰性填充**只追加在尾部、决定性内容留在头部**——故它**对「尾部被静默丢弃」本身是盲的**，不能靠它声称「无截断」。
- **但输入 token 随字符数单调增长**：字符增量 5,994 / 6,993 / 999 / 444 / 7,548 / 15,984 对应 token 增量 810 / 945 / 135 / 60 / 1,020 / 2,160，**恒为约 12 token / 111 字符**。**任何固定的字符上限都会让上限之上的 token 数冻结——它没有。**
⇒ 故结论成立：**上限是插件的**。但**provider 侧的真实上限仍未触及**（未找到拒绝点，也未做尾部决定性内容的判定）。

**同一构造**（`DECOY + filler + CORRECTION`，**决定性内容置于最末尾**）：

- **Laya 在 ~3,082 字符处丢失证据、答案翻错**，而 `fits: true`、无 `truncated`、无 warning；
- **Jev 在 15,002 字符处仍取用末尾证据并答对**（0.97）；**第三轮直连路线进一步证到 39,927 字符**（§5.3）。

→ **相差约 4.9 倍（按接入层的 15,002 计；provider 侧上限未触及，故该倍数只增不减），且失败方式根本不同：Laya 静默丢输入，Jev 要么容纳要么告警。**
→ **这是 D1 判定「Jev 不可替代」的实质依据**，且现在有实测支撑。

**必须连同启动配置与所查询 checkpoint 报告**（§4.8）：同一份代码，english 单载 → 钳位 **1024**；english 在三载 loadout 下 → **512**；而同机的 multilingual 与 typed-decisions 仍为 **1024**。（P18 每个 loadout 只启动一次，**未做确定性重复**。）
→ **「Laya 的窗口是 512 token」是不完整的表述，对另一个操作者可能错 2 倍。**

### 5.3.1 窗口在真实的累积运行中如何侵蚀（P24）

**设置**：3 个会话 × 20 步，每步向一个**被携带的 ledger**追加一条记录；每步向两个判定器各问一次。

| 指标 | 值 |
|---|---|
| 总步数 | 60 |
| **窗口内可问的步数** | **14 / 60（23%）** |
| **首次溢出** | **step 14** |
| 最终状态 | **1,751 token / 6,875 字符** = 钳位的 **3.4 倍** |
| Laya 逐会话准确率 | 会话 0：1.000（n=14，**6 步被跳过**）；会话 1、2：**n=0，全部溢出** |
| LLM 逐会话准确率 | **1.000 / 1.000 / 1.000**（n=60）|

→ **在一个 60 步的累积运行里，本地判定器只有前 23% 可用。**
→ **LLM 三会话全部 1.000**——**本任务上累积未造成漂移**，但这**又一次触顶**，故**不能据此声称 LLM 不受累积影响**。

### 5.3.2 截断是否**改变答案**：**未能测出**（P26，存在位置混淆）

P24 只说明**窗口何时用尽**；P25 试图测「用尽是否伤害判断」，但**探针无效**（题目把答案说出来了，删除对照 0/6）。
P26 施加了**证书**后重做——决定性内容是**叙述性更正**、位于**尾部**，问题**只问结论**，**题面既不含 v0 也不含 v1**；两臂唯一差别是**该更正是否存在**。

状态 **1,969–1,982 token** vs **512** 钳位：

| 单元 | n | **选中「更正前」值** | 答出「更正后」值 |
|---|---|---|---|
| **full（更正存在）— Laya** | 10 | **10 / 10** | **0 / 10** |
| dropped（更正删除）— Laya | 10 | 10 / 10 | 0 / 10 |
| **full — LLM** | 10 | 0 / 10 | **10 / 10** |
| dropped — LLM | 10 | 10 / 10 | 0 / 10 |

**读法**（与直觉相反，必须说明）：dropped 臂答「更正前」值是**按构造成立**的（该臂里没有更正），故**诊断量不是「full 比 dropped 好」，而是「full 能否把两个状态区分开」**。

**⚠️ 该探针有两处致命设计缺陷；早期版本声称「复核时补做了缺失的对照」，该对照【未持久化】，其数字已撤回（第七轮）。**

**缺陷一（更根本）：两臂的可见前缀完全相同 ⇒「两臂同答」是构造的必然，不是测量。**
dropped 臂只删掉 `[c1]` 那一行，状态仍有 **1,955–1,965 token ≈ 4× 钳位**。逐 token 核验：**两臂的前 512 个 token id 在 10/10 条上完全相同**，而更正所在位置是第 **1,943–1,952** 个 token。**【不可核验 ⚠️ ERRATA §10.2】**：该 token 位置无 `results\` 产物（同 §8.7(a) 处的标注）；「前 512 个 token id 相同」这一条**可由 P26 的 `in_pad` 与选项记录间接支持**，但绝对位置不可核验。
⇒ 截断发生在两者**共同的尾部之外**，两臂喂给判定器的可见内容**逐位相同**。「两臂给出相同答案」因此**由构造强制成立**，对「截断是否改变答案」**零信息量**。

**缺陷二：选项顺序与答案完全共线。** 选项由 `sorted({v0, v1, v0+77})` 生成，恒有 `v0 < v0+77 < v1` ⇒ **诱饵恒为 o01、真值恒为 o03**；Laya 在 10/10 行都选 **o01**（首位）。论文 §4.5 自测的位置效应（首位 1.00 vs 其他 0.125）**足以单独解释**该结果。

**补做的对照（本文原缺，复核时新增）**：**去掉填充**，使更正落在窗口**之内**（状态 **79–92 token**，`truncated = false`）：

| 单元 | n | 答出「更正后」值 | 答出「更正前」值 |
|---|---|---|---|
| 截断臂（P26 原设计，512 钳位） | 10 | 0 / 10 | **10 / 10** |
| **对照臂（填充去除，更正可见）** | 10 | **6 / 10** | **4 / 10** |

⇒ **⚠️ 已于第七轮撤回**：早期版本在此写「截断确实抬高『答更正前』的比例：0.40 → 1.00（Fisher p = 0.011）。**截断伤害是真的**」。**这组数字（含 p = 0.011）没有任何产物**，其状态规模恰等于 P26 已废弃的原型，**故不得作为结论**。下方第 2 条与「裁定」两处同样使用该数字，一并撤回。
⇒ **⚠️ 本条的定量拆分已撤回（第七轮）**：早期版本写「该效应约 **6/10 来自截断**，另 **4/10 是「更正完全可见却未被采纳」**」。**这组数字（6/10、4/10、状态 79–92 token、Fisher p = 0.011）在整棵树中没有任何产物**——没有行、没有脚本、没有花费记录，只存在于论文正文与 `protocol\AUDIT-FINDINGS.md`；**且其状态规模恰好等于 P26 自己【已废弃首版原型】的状态规模**，而该原型的报告原文是「根本没有可截断的东西」。**本树无法区分「一次新的对照运行」与「被丢弃原型的数字」。**
⇒ **现在能说的**：P26 的产物显示**两臂在 512 token 的可见前缀上逐位相同**、更正位于窗口之外（**构造的必然**）；**「截断会发生」有产物支撑**（P24：60 步只有 14 步能塞进窗口；P26：20 次调用全部 `in_pad = 512`、`truncated = true`）。
⇒ **不能说的**：「截断改变了答案」——那需要一个把更正移入窗口且**被持久化**的对照。故本条**降级为「截断确实发生，其伤害未能与位置效应分离」**。

→ 因此原先的两条陈述都要限定：
1. **截断确实发生**（独立成立）：20 次调用全部 `in_pad = 512`、`truncated = true`；P3 又证明钳位后输出逐位冻结。
2. **⚠️ 撤回**：早期版本在此写「截断确实抬高错误率（0.40 → 1.00，p = 0.011）」——**该对照臂无产物**，见上。**仍成立的部分**：P26 原设计的「两臂同答」**是构造的必然**，不足以证明任何因果。
3. LLM 的 full 1.000 / dropped 0.000 只反映**更正文本是否出现在状态里**（LLM 上下文 1M，从不被截断），**不构成对 Laya 截断后果的对照**。

**裁定（第七轮修订）**：**截断会发生（P24，有产物）**；**但「截断抬高错误率」所依据的对照臂无产物，故该因果关系不予断言**。早期版本的裁定写「也会抬高错误率（本对照臂，p = 0.011），但它是部分原因」并援引「另有 4/10 的失败发生在证据完全可见时」——**两处数字均已随该对照臂撤回**。⇒ **最终裁定：截断确实发生；其伤害未能与位置效应分离。**

>
> **⚠️ 第八轮最新进展（在本条撤回【之后】取得）：该对照臂已被重新造出，并落在被撤回的数字上。**
> `rerun/p26_control_low_window.py` 按文件路径导入 **P26 自己的 `build_item`**，同一 seed、同一 RNG 调用顺序，
> **只改填充**，使更正落入 512 token 窗口；**填充规则在读取任何判断结果之前就已定下**
> （取中位状态最接近被撤回臂所称 79–92 token 的最小 `PAD_REPEATS`，而 `PAD_REPEATS=0` 恰好给出 79–92）。
> **结果**：状态 **79–92**（中位 85）、答更正后 **6/10**、答更正前 **4/10**、Fisher 双侧 **p = 0.010836**——
> **四个被撤回的数字全部独立复现**；同状态下 LLM 臂 **10/10**。
>
> **⇒ 撤回的理由被【解决】而非被证实**：原型与本对照之所以重合，**是因为它们是同一个生成器在同一填充下的产物**
> ——**那个看起来要命的巧合是确定性的后果，不是造假的证据。**
>
> **⇒ 实质性主张（截断把「答更正前」的比例从 0.40 抬到 1.00）现在有产物支撑，可以恢复。**
> **但恢复与否留待作者裁定**：这是本项目**唯一一条【向上】的修正**，且它推翻的是一个**在当时证据下正确作出**的决定，
> 故不应被顺手带过。产物在 `rerun/P26-control-low-window.json`（刻意置于 `results/` 之外，
> 因 `p30_inventory.py` 会遍历 `results/*.json`，放入会静默改变论文的产物计数）。

## 5.4 本节结论：约束是**延迟与窗口**，不是美元

| 轴 | 分离程度 | 方向 |
|---|---|---|
| **单次成本** | 三者全在 10⁻⁵ 美元量级；**无实质分离** | — |
| **延迟** | **p50 跨约 25–32 倍**（37.4 ms → 671 ms → **0.9–1.2 s**，下沿/上沿分别取自合并 n=35 的中位与唯一有产物的那次运行——**两次运行的说法已于第七轮撤回**）；Jev 合并实测 max 4,018.6 ms | 有利于本地 |
| **状态窗口** | **约 4.9 倍**，且失败方式不同（静默 vs 告警） | 有利于远程 |
| **失败可观测性** | Laya **静默**；Jev **告警** | 有利于远程 |

→ **中心主张改写为**：
> **在长线任务中，把判断交给本地小判定器的收益不在成本（成本本就不是约束），而在于它不占用顺序往返；代价是它的可用状态窗口小一个量级，且越界时静默失败。**
> **⚠️ 该主张的长线部分只由缩减版验证**（P24：同一进程内 3×20 步；**自主长线运行未执行**，见 §10.1）——「不占用顺序往返」这一条在**单步**层面成立，在**长线**层面属未测。

这一表述**比「更便宜」更窄、更硬，且避开了最容易被反驳的一点**：LLM 也能用 context 缓存把输入压到 $0.003/1M，因此「LLM 贵」在算术上站不住。

## 5.5 限制

1. **成本与延迟均为描述性**：LLM n=48、**Jev n=35**、Laya n=30，且**单机、单网络路径、单一时段**。
2. **Jev 与 LLM 的延迟含传输**，故**不可与 Laya 的本地延迟视为同类量** —— 三者都标了限定词。
3. **未记录采集时段落在峰价还是谷价**，故成本数字可能随运行时刻变化（峰谷差 2×）。
4. **Laya 成本未货币化**（自托管算力），故「≈$0」是**边际**成本，不含硬件摊销。**论文不得据此宣称 Laya 在所有意义上免费。**
5. **LLM 的 1M 上下文是文档值，未实测**；Jev 的**插件侧 16,000 字符常量**只证到 15,002（厂商文档 `state` 上限为 32k token，**未实测**）。
6. **未测**：LLM 在长 state 下的成本与延迟（其成本对不缓存输入为 $0.15/1M，长任务下会显著变化）。
