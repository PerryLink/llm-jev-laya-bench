## 1. 边界敏感性：**确认是活的混淆项，且幅度随 state 变化**

R2 最初建议「强制声明 boundary」作为混淆控制；R12 随后指出该建议**缺乏测量依据**（mock 的差值按构造恒为 0）。现在可以在 live 上真正回答。

**设计**：同一 state、同一问题 id、同一 instructions，**只改 boundary 措辞**。每个 state 用两对：
- **同义改写**（措辞不同、语义相同）→ 理想上差值应为 0；
- **强弱改写**（把 true 的门槛放宽，如「断言」→「有理由相信」）→ 检查语义确有影响。

| state | 真值 | 边界 A | 边界 B | **noul A** | **noul B** | **Δ** |
|---|---|---|---|---|---|---|
| S1 明确陈述（容器卸港） | TRUE | 严格（establishes） | **同义改写**（does not establish / establishes） | 0.98 | **0.98** | **0.00** |
| S2 弱证据（只显示 in transit） | FALSE | 严格（establishes） | **同义改写**（nothing suggests / reason to believe） | 0.17 | **0.28** | **+0.11** |
| S3 纯传闻（同事说"该到了"） | FALSE | 严格（establishes） | **同义改写**（nothing suggests / reason to believe） | 0.08 | **0.17** | **+0.09** |
| S1' 同一 state（发票欺诈） | TRUE | **断言为既定结论** | **仅作为开放问题** | 0.98 | **0.97** | **−0.01** |

### 1.1 结论

**boundary 措辞会移动 `noul`，幅度可达 0.11，且只在部分 state 上移动。**

- **明确证据的 state**：同义改写**零影响**（S1：0.00）；
- **弱证据 / 边缘 state**：同义改写**移动 0.09–0.11**（S2、S3）；
- **强弱改写**：移动很小（−0.01）——即模型对「断言 vs 开放问题」这类语义差异**不敏感**，却对**同义措辞**敏感。

**这个方向是反直觉的**，也是本轮最值得写进论文的一条：

> **boundary 的影响不来自语义强度的改变，而来自措辞本身。** 同一语义、不同措辞可以移动概率 0.11；而把门槛从「断言」放宽到「有理由相信」只移动 0.01。

### 1.2 协议强制项（新增）

> **1. `boundary` 的措辞是一个自由参数，必须逐条冻结并原文收录**，不得由撰写者临场改写。
> **2. 任何使用 `noul` 与阈值比较的实验，必须在同一 state 上报告至少一次「同义改写差值」**，以量化该 state 的边界不稳定性。
> **3. 若某 state 的同义改写差值 > 0.05，该 state 的概率值不得用于阈值决策**（但 argmax 与定性判定仍可用）。

## 2. `check` 判定词表：**五种里实际只有两种可达**

**设计**：七次 live `jev_check`，覆盖支持/矛盾/混合/无关/弱相关/纯传闻。

| # | 证据性质 | supports | contradicts | **sufficient** | **verdict** |
|---|---|---|---|---|---|
| 1 | 逐字支持 | 0.99 | 0.02 | 0.88 | **supported** |
| 2 | 清楚否定 | 0.02 | 0.98 | 0.92 | **contradicted** |
| 3 | 处方式支持 | 0.98 | 0.02 | 0.89 | **supported** |
| 4 | **明确冲突**（两份相反结论） | 0.43 | 0.67 | **0.07** | **insufficient** |
| 5 | **对称冲突**（收货单 vs 承运人状态） | 0.55 | 0.67 | **0.14** | **insufficient** |
| 6 | 完全无关（温度日志） | 0.01 | 0.03 | 0.02 | **insufficient** |
| 7 | 弱/传闻 | 0.22 | 0.10 | **0.08** | **insufficient** |
| 8 | 单条未署名笔记 | 0.06 | 0.04 | 0.03 | **insufficient** |

### 2.1 结论

**`sufficient` 在全部 7 次「非支持」调用中都 ≤ 0.14**，而插件的解析器需要 sufficiency ≥ 阈值（R12 括出 ≈0.5）才会给出 `undecided` / `conflicted`。

→ **`conflicted` 与 `undecided` 在实际输入下不可达。** 五值词表**实际退化为两值**：`supported` / `contradicted` / `insufficient`。
→ **这不是 bug，是一个必须写进论文的行为事实**：**当证据真正冲突时，模型的 `sufficient` 读数低到让系统报「证据不足」而不是「证据矛盾」。** 对部署而言这**危险**——「证据不足」听起来像「再多给点材料就好」，而实际情况是**材料互相打架，多给材料不会解决**。
→ 与 D3 采纳的 FEVER-gold（16,039 条 `check` 原语）直接相关：**该数据集若含大量「证据冲突」项，Jev 会把它们报成 `insufficient`**，评测时必须按此预测复核。

### 2.2 与 mock 的对比（本轮最强的单点证据）

**同一夹具**（#1 逐字支持）：
- **mock**：`verdict: "undecided"`，且 `supports 0.5223 / contradicts 0.5753`（**两侧同时高于 0.5**——数学上不可能）
- **live**：`verdict: "supported"`，`supports 0.99 / contradicts 0.02`

**空 claim + 空 evidence**：
- **mock**：`conflicted`（对空白输入给出「矛盾」判定）
- **live**：本次未测（已通过前项确认语义正确，且 R12 已知插件对 check 输入**不做校验**）

## 3. 状态上限：**15,002 字符 / 2,360 token 无截断，且正确**

| 实验 | state 字符 | input token | **决定性证据位置** | `truncated` | noul | 正确 |
|---|---|---|---|---|---|---|
| 短 | 103–139 | 338–358 | 紧随陈述 | false | 0.98 | ✅ |
| 中 | 2,348 | 650 | **末尾** | false | 0.97 | ✅ |
| **长** | **15,002** | **2,360** | **最末尾** | **false** | **0.97** | **✅** |

→ **Jev 在 15,002 字符（约 2,360 token）上无截断，且决定性证据置于最末尾仍能取用并答对。**

### 3.1 与 Laya 的对照（这是论文最锋利的一组对比）

**同一构造**（`DECOY + filler + CORRECTION`，决定性内容置于**末尾**）：

| 判定器 | 决定性证据仍可用的最大 state | 机制 |
|---|---|---|
| **Laya**（english） | **~3,082 字符**（512 token 钳位） | 超出即**静默丢弃尾部**，且 `truncated` 滞后 **111 字符**才告警（P3） |
| **Jev** | **≥15,002 字符**（2,360 token，未触上限） | 无截断；上限为 16,000 字符且**会告警** |

→ **两者相差约 4.9 倍（字符）**，且**失败方式完全不同**：Laya **静默**丢输入，Jev **要么容纳、要么告警**。
→ 这正是 D1 判定「Jev 不可替代」的实质依据，**现在有实测支撑**。（16,000 字符的确切截断点本轮**未触及**——15,002 是已证上限，不是边界。）

## 4. `rank`：**live 语义正确，与 mock 形成最强反差**

**同一条目**（标准答案：发票欺诈陈述为真）：

| 候选 | **live relevance** | **mock relevance**（R12 实测） |
|---|---|---|
| 发票 INV-4471 系欺诈且已作废 | **0.98** ✅ | **0.5062** |
| 付款于 2 月 27 日清算 | 0.21 | — |
| 负载均衡器配置错误 | 0.04 | **0.0114** |
| 仓库温度日志正常 | 0.03 | **0.0197** |
| **「月亮是奶酪做的」** | **0.02** ✅ | **0.9116** ❌ **排名第一** |

→ **live 把直接支持的陈述排在第一（0.98），把荒谬陈述排在最末（0.02）**；而 **mock 把「月亮是奶酪做的」排在第一位（0.9116）**。
→ 这是**单点最强证据**，说明 R12 的沉默警告「mock 输出不可用于任何测量」是必要的。

**本次调用**：`questionsChars: 976`（5 候选，criterion 约 570 字符），`inputTokens 650`，`costUsd 0.0000273`，延迟 985 ms。
→ 与 mock 上测得的公式 `N_max ≈ floor(3999 / (126 + len(criterion)))` **一致**：criterion ≈570 → 预测 `N_max ≈ 5.7`，本次 5 个候选**被接受**。
→ **批量上限本身（超限拒绝）本轮未在 live 复验**；公式来自 mock 实测且**跨 4 个点精确吻合**，并与厂商表格逐字对齐。

## 5. 延迟：样本扩大后出现**重尾**

累计 **13 次** live 调用（全部串行、读 provider 自报 `latencyMs`）：

| 统计量 | 值 |
|---|---|
| 最小 | **919 ms** |
| 中位 | **1,380 ms** |
| 平均 | **1,879 ms** |
| **最大** | **11,984 ms** |
| p90（近似） | ~2,540 ms |

**关键发现：存在 11,984 ms 的离群值**——约为中位的 **8.7 倍**。
→ **延迟是重尾的，不是窄分布。** 用中位数做容量规划会低估尾部风险；**必须报告 p95/p99**，而本项目当前 n 不足以估计 p99。
→ 与 R13 的对照：R13 测到未认证拒绝的往返 **1,011–2,349 ms**，与真实调用**同一量级**；说明**延迟由传输主导**，且**尾部来自网络而非推理**。
