## 0. 为什么做这一轮

论文 §10.1 第 11 条如实列着：**Jev 的全部数字没有机器可读产物** —— 27 个（当时）`results\*.json` 中没有任何一个含 Jev live 数据，`evaluate.py` 的 live 路径仍是 `NotImplementedError`，Jev 的数字只有 `probes\P12`／`P13` 两份 markdown 出处。**（第五轮补记：`evaluate.py` 的 live 路径**已实装**——`LiveJevJudge.answer()` 现调用 `jev_client.ask`，`__main__` 仅在其 `verify()` 通过时准入该臂；真实网络路径未实测。本条缺口已由 `src\instrument\jev_client.py` 与 `results\P27*.json` 关闭。）**
而 P13 的汇总统计量**算术上不可能**（见 `results\ERRATA.md` N-1）。所以 Jev 那一列是全文**唯一**没有产物支撑的一列。

本轮把它补上。做法不是「再写一份 markdown」，而是**建一条可复现的 live 传输路径**，让每个数字背后都有 JSON。

## 1. 路线与交叉验证

`jev_measure.py` 原本的设计是「**agent 持有 Jev 工具，由 agent 执行、把响应写回；脚本只负责分析，不负责传输**」。本轮沿用这个分工，但把它**落到可复现的代码上**：`jev_client.py` 直接打同一条路线。

**这条路线的形状是实测出来的，不是从文档读来的**：

```
POST https://openrouter.ai/api/v1/systemone
Authorization: Bearer $OPENROUTER_API_KEY     (DSH 凭据库 ref，值从不落盘)
{"model": "typesafe/jev-1.13", "state": ..., "questions": {...}}
```

**交叉验证（同一条请求，两条路线）**：

| 字段 | 直接路线（本客户端） | DSH `jev_ask` 插件 |
|---|---|---|
| `noul` | **0.98** | **0.98** |
| `input_tokens` / `inputTokens` | **347** | **347** |
| `cost` / `costUsd` | **0.000014574** | **0.000014574** |
| 解析后的模型 | `typesafe/jev-1.13-20260917` | `typesafe/jev-1.13-20260917` |

⇒ **两条路线是同一个仪器**，故本轮的测量与早期探针测的是同一个东西。

## 2. 新发现（只有走直接路线才能看到的）

### 2.1 provider **不返回** `band` / `probability` / `truncated` / `latencyMs`

provider 的原始响应**顶层只有** `{model, provider, id, answers, usage}`，而**答案对象的键随原语而变**（`P27d`，三个原语各实测 1 次）：

| 请求原语 | provider 返回的答案键 |
|---|---|
| `noul` | `type`, `noul` |
| `choice` | `type`, `choice`, **`probabilities`**, **`confidence`** |
| `score` | `type`, `score`, `legend`, **`probabilities`**, **`confidence`** |

**⚠️ 归属结论必须按原语限定。** 本报告初稿据 `noul` **一例**写成「答案对象里只有 `type` 与 `noul`」——**那是过度推广**，补测 `choice` / `score` 后发现它们另外返回 `probabilities` 与 `confidence`。更正后的归属：

| 字段 | 来源 |
|---|---|
| `type`、`noul`、`choice`、`score`、`legend`、`probabilities`、`confidence` | **provider** |
| `probability`（**单数**）、`answer`、`band` | **接入层推导** |
| `truncated`、`stateChars`、`questionsChars`、`redactions` | **接入层出口记账** |
| `latencyMs`、`warnings` | **接入层** |

**在三个原语下都未由 provider 返回**的字段（实测 `never_returned_by_provider`）：`band`、`probability`、`answer`、`truncated`、`stateChars`、`questionsChars`、`redactions`、`latencyMs`、`warnings`。
⇒ **`confidence` 与 `probabilities`（复数）是 provider 字段**，**不得**列入「自报不可信」清单。
⇒ **教训（已写入 §6.4.1）**：**字段归属必须逐原语实测，不能从一个原语外推**——这与论文 §4 所述「把测量装置的属性当成被测对象的属性」是同一个错误类的一个新面孔。

⇒ `band`、`probability`、`truncated`、`stateChars`、`questionsChars`、`redactions`、`latencyMs` **全部是接入层（DSH 插件）合成的**。
**这是论文 Result B 框架「从线上直接看到」的证据** —— 此前只能从插件自己的输出反推。

### 2.2 `probability` = P(所答选项)，**双向确认**

| 插件返回 | `answer` | `noul` | `probability` | 判据 |
|---|---|---|---|---|
| T1 状态 | `true` | 0.98 | **0.98** | `probability == noul` ✓ |
| T2 状态 | `false` | 0.02 | **0.98** | `probability == 1 − noul` ✓ |

⇒ R12 的 T-1 陷阱**在 live 上双向复现**。且既然 provider 根本不返回该字段（§2.1），它就是**接入层的推导规则**，不是 provider 的语义。

### 2.3 判据确实参与判断（与 mock 的对照）

同一状态、三种判据措辞：

| 判据 | `noul` | 输入 token |
|---|---|---|
| explicit | **0.97** | 340 |
| reversed | **0.91** | 342 |
| terse | **0.96** | 316 |

⇒ **live 上判据会移动答案**（0.91–0.97）。
**对照**：mock 上同一操作移动了**恰好 0.0000**，而 `questionsChars` 从 216 变到 198 —— 即判据被序列化、被计数、却从未进入哈希。**这个对照现在两侧都有实测。**

### 2.4 16,000 字符上限**是插件侧的** —— 实测证明

直接路线接受了 **39,927 字符**（5,728 输入 token），状态阶梯单调上升、无截断：

| 状态字符 | 输入 token | `noul` |
|---|---|---|
| 1,965 | 598 | 0.97 |
| 7,959 | 1,408 | 0.97 |
| 14,952 | 2,353 | 0.97 |
| 15,951 | 2,488 | 0.97 |
| 16,395 | 2,548 | 0.97 |
| 23,943 | 3,568 | 0.97 |
| **39,927** | **5,728** | 0.97 |

⇒ 插件文档化的 16,000 字符上限**不是 provider 的上限**（provider 接受了 2.5 倍）。
**这条此前只能靠读插件源码断言，现在是实测。** 论文的「Jev 窗口 ≥15,002 字符」因此必须限定为**接入层窗口**；provider 侧的真实上限**未触及**。

### 2.5 插件的 `latencyMs` 自报约为**尺寸匹配**墙钟的 **1.94 倍**（第五轮更正）

| 测量 | n | p50 | mean | min | max |
|---|---|---|---|---|---|
| 插件自报 `latencyMs` | 7 | **1,851 ms** | 2,026 | 1,233 | 3,141 |
| 本客户端墙钟（**本产物重跑后**） | 20 | **1,192 ms** | 1,551 | 847 | **4,019** |
| ↑ 同一脚本**上一次**运行（本报告原印的那组） | 20 | 915 ms | 1,001 | 848 | 1,802 |

⇒ 同一路线、同一状态下，**自报延迟约为实际往返的 2 倍**。
**⚠️ 必须声明的限制**：两组**不是同时配对**采集的（插件那批是另一阵发），故差距里可能含网络漂移；n=7 vs n=20 也不足以隔离「插件开销」与「线路变化」。**本文把它记为一条待验证的旗标，不是结论。** 且该旗标现**更强**：直接路线重跑后的**最大值**为 **4,019 ms**，**高于**插件自报的中位数（1,851 ms）——即「插件比直连慢」这一读法在重跑后**不再成立**，1.94 倍只对**尺寸匹配**的那一类状态成立。

## 3. 延迟：跨 **127 倍**状态范围基本平坦

墙钟独立测量（`P27c`，每档 5 次）：

| 状态字符 | 输入 token | **p50** | min | max | 成本 |
|---|---|---|---|---|---|
| 126 | 347 | **956 ms** | 855 | 2,172 | **$0.0000146** |
| 7,896 | 1,400 | **881 ms** | 864 | 1,897 | **$0.0000588** |
| 15,999 | 2,495 | **1,073 ms** | 939 | 1,873 | **$0.0001048** |

⇒ **状态放大 127 倍，p50 只从 956 变到 1,073 ms** —— 延迟由**传输**主导，不由状态大小决定。这与论文「延迟由传输主导，推理几乎不增加时间」的判断一致，且现在有了剂量-反应式的支撑。
⇒ **成本则随输入 token 单调上升**（$1.46e-5 → $5.88e-5 → $1.048e-4）。

**合并（`P27` n=20 + `P27c` n=15）**：

| 判定器 | p50 | n | 测量点 |
|---|---|---|---|
| **Laya**（本地 cuda） | **37.4 ms** | 30 | 墙钟，批大小 1 |
| **LLM**（非思考） | **671 ms** | 48 | **provider 自报** |
| **Jev**（openrouter） | **1,073.4 ms**（mean 1,407 / min 847 / max 4,019） | **35** | **墙钟（本客户端）**；⚠️ **单次抽样**——同一脚本两次运行 p50 相差 30%、max 相差 123%，故论文报**区间** **0.9–1.2 s** |

⇒ **Jev/Laya ≈ 25 倍**（原论文写 **37 倍**，那是基于插件自报的 1,380 ms）。
⇒ **⚠️ 三个数字的测量点仍不完全同口径**（LLM 是 provider 自报），论文必须逐列标注，不能混读。

## 6. 限制（如实列出）

1. **provider 侧窗口上限未测**：只证到 39,927 字符被接受；未找到拒绝点。
2. **延迟与插件自报的差距未隔离**（n=7 vs n=20，非同批采集）——记为旗标。
3. **单机、单网络路径、单一时段**：延迟随位置与时段变化（本项目的 Laya/Jev 对照同样受此限）。
4. **`latencyMs` 的自报偏差只在一条路线上观察到**；TypeSafe 路线未测（该路线不报成本）。
5. **8/8 是模板化条目**，不是能力估计。
6. **OpenRouter 是接收 state 的第三方**，与 TypeSafe 路线的保留策略不同；论文的 Jev 数字均标注为 **openrouter 路线**。
