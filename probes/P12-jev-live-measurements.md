8 个真值明确、四对正反的条目（发票/故障/物流/临床），每对一真一假：

| 条目 | 真值 | noul | answer | band | 正确 |

**准确率 8/8。** 但注意出题偏向：**四对全是清晰的显式陈述**，所以这个 100% **只说明「state 明确陈述时 Jev 正确」**，**不说明它在需要解释的任务上强**。按本项目已建立的判据，这类任务正是 Laya 也能拿 1.00 的区制（P8）。**不得据此主张 Jev 的普遍准确率。**

### 1.1 R12 陷阱 T-1 **在 live 上确认**

T2 返回 `answer: "false"`、`noul: 0.02`、**`probability: 0.98`**。
→ **`probability` 是「所选选项的概率」，不是 P(true)。** 把 `probability` 记为 P(true) 会把这一半条目**反号**。
→ 8/8 全部满足 `answer=="true" ⇒ probability==noul` 且 `answer=="false" ⇒ probability==1−noul`。

**同时发现一个更细的语义**：**`band` 跟随 `noul`，不跟随 `probability`**（T2/T4/T6/T8 的 noul=0.02 → band="no"；noul≥0.98 → band="yes"）。
→ 所以同一响应里有**两个**「置信度类」字段，**方向相反**：`probability` 朝向所选答案，`band` 朝向 true。**协议必须只记录 `noul` 作为 P(true)，`band` 可作三值化，`probability` 只作诊断。**

| **输出 token** | **恒为 20** |

### 3.1 推翻「Jev 输出不计费」

我在 R2 §C.1 记录过「输出 **$0**，不计费」（来自 TypeSafe 路线文档）。**OpenRouter 路线是计费的**——`outputTokens: 20` 且成本随 token 变化。
→ **两条路线的计费模型不同**，**不得混用一张成本表**。D1 与我此前的成本讨论都以「输出免费」为前提，**该前提只对 TypeSafe 路线成立，对本项目实际使用的 OpenRouter 路线不成立。**

### 3.2 对成本结论的影响

单次约 **$0.000015**。设计里 120 个检查点/运行 → Jev 判定层约 **$0.0018/运行**。
→ 与 LLM 结构化判定（约 $0.00011/次，同规模 state）相比，**Jev 便宜约 7 倍**。
→ **「钱不是约束」的结论不变**（两者都在十万分之一美元量级），**但「Jev 更便宜」这一次是有真实计量支撑的**，不再是推测。

## 7. 限制

1. **n 很小**（9 次调用的延迟/成本，8 个条目的准确率）。**延迟与成本是描述性的，不是精确估计。**
2. 夹具是**为清晰而撰写的合成状态**，不含真实语料 → **零新增出境风险**，但也意味着**未测真实分布的输入**。
3. **单机、单一网络路径、单一时段**；未记录该时段是否落在 OpenRouter 或 TypeSafe 的峰谷定价窗内 → **成本数字可能随时段变化**。
4. **`model` 解析为 `typesafe/jev-1.13-20260917`**：钉死了版本 ✅，但**上游若下线该日期版本，复现需换版本并重跑**。
