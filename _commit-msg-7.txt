Erratum: the token-density claim named the wrong text, and understated the real defect

Corrects a factual claim in both manuscripts, in the records it came from, in three
decision documents that adopted its constant, and in the instrument's own docstring.
Adds the measurement as an artifact, a gate invariant, and a sixth defect the paper
was missing.

WHAT WAS WRONG

Section 3's defect 3 said the planner "measures ~6.33 chars/token on English prose ->
overestimates by about 1.8x". Three independent checks agree:

  * English prose measures 4.31 chars/token, not 6.33.
  * 6.33 is the density of this project's own truncation-sweep state, which is
    DECOY + FILLER*45 + CORRECTION -- one filler sentence repeated 45 times.
  * Re-measured with the exact constants from p3_clamp_calibration.py:57-60, that
    state gives 6.782, so the over-estimate there is 1.949x, not 1.82x. The R13
    token column runs 7-8% high.

So the sentence attached a correctly measured number to the wrong object AND
stated a magnitude its own source did not support -- this paper's named error
class, inside the paper.

WHAT THE CORRECTION ADDS, WHICH MATTERS MORE

The direction that actually matters was never reported. Measured against the
shipped tokenizers, the estimator OVER-reserves on prose (1.239x) but
UNDER-reserves on JSON 1.450x, source code 1.075x, Chinese 2.105x and CSV
2.150x. Those are the inputs planning.py's own docstring says it serves. On them
the preflight answers `fits: true` for a state the model then silently truncates
-- the failure the preflight exists to prevent. The 1.15 "safety" factor does not
cover it; for prose its entire benefit is 3-4 characters.

The one input type the paper measured was the most favourable the estimator could
be handed, because repetition raises compressibility monotonically (x1 = 5.550,
x100 = 6.920 chars/token).

WHY IT SURVIVED EVERY EARLIER AUDIT

A ratio carries no record of the text it was measured on. The number and its
object were both present and correct; only their attachment was wrong, and no
check compared an attachment. The figure was also reproducible on re-run, so the
usual "can this be reproduced?" test passed.
