# R8 — 主控实测：截断边界逐 checkpoint 标定，以及对 V3/V4/V5 的最终裁决

> 作者：主控（一手实测）
> 本文件包含**我自己新测得的数据**，它修订了 R2/R13 关于截断窗口的表述，并解决了 V3 提出的「512 钳位是否仅限英文」问题。

## 1. 我实测的钳位标定（一手，三 checkpoint）

**方法**：构造 `DECOY + filler(n) + CORRECTION`（决定性更正置于**尾部**），2 选项 noul（criteria 已声明），逐字符递增，读 `usage.input_tokens_padded` 与 `truncated`。
**注意**：本机 sidecar 以 `--max-len 1024 --head-max-len 512` 启动，三个 checkpoint 均已加载。

### 1.1 English（`convaiinnovations/laya` 根）

| 字符 | `input_tokens_padded` | `truncated` | noul |
|---|---|---|---|
| 2417 | 422 | no | 0.3889 |
| 2750 | 470 | no | 0.5827 |
| 2972 | 502 | no | 0.5399 |
| **3083** | **512** | **no** ← 已钳位，**字段仍说没问题** | 0.3002 |
| **3194** | 512 | **yes** | 0.3594 |
| 3971 → 7967 | 512 | yes | **0.3594（恒定）** |

→ **钳位点 = 3083 字符（512 token）**；**`truncated` 首次触发 = 3194 字符**；**静默窗口 = 111 字符**。
→ **3971→7967 字符之间 `noul` 恒为 0.3594**，**再次独立复现「输出冻结」**。

### 1.2 multilingual（`subfolder=multilingual`）

| 字符 | `input_tokens_padded` | `truncated` | noul |
|---|---|---|---|
| 2972 | 482 | no | 0.3756 |
| **3083** | **497** | no | 0.3189 |
| **3194** | **512** | **yes** ← 钳位**与**告警同时到达 | 0.1813 |
| 3971 | 617 | yes | 0.3791 |
| 6302 | 932 | yes | 0.2934 |
| **7967** | **1024** | yes | 0.0498 |

→ **钳位点 = 1024 token，而非 512。** 该 checkpoint 的窗口是英文的 **2×**。

### 1.3 typed-decisions（`subfolder=typed-decisions`）

行为与 multilingual 同族：3083 字符 → 518 token（未钳位）；8078 → 1024（钳位），16070 → 1024，输出冻结。

### 1.4 **结论：钳位与 checkpoint 绑定，不是全局常量**

| checkpoint | 实测钳位 | 规划器以为（Path A，Planner `max_len`） |
|---|---|---|
| english | **512** | 1024 → **乐观 2×** |
| multilingual | **1024** | 1024 → **一致** |
| typed-decisions | **1024** | 1024 → **一致** |

**裁决 V3 的指控：成立。** V3 说「512 钳位仅限英文，P10 的截断曲线会按 2.3× 过小的预算计算」——
**实测证实方向，但幅度需修正**：英文窗口 512、多语 1024，即 **2×**（V3 估的 2.3× 接近但更保守）。
→ **R13 把 512 当作全局常量是错的**；R13 的 §2.3 只在 english 上测量，然后推广到了全族。**这是 R13 报告中最重要的一处过泛化。**

**对论文的后果**：
1. **截断曲线必须逐 checkpoint 分别标定**，不能用一个 `W`。R15 §3.5 的 `integrity(t)=1[tokens≤W]` 中 `W` 应为**每 checkpoint 一个值**。
2. **多语/typed-decisions 的可用 state 是英文的 2 倍** → 若论文选 english 作主 checkpoint，它是最保守的选择，**应在论文中说明这是下限而非上限**。
3. **`truncated` 与真实钳位的关系逐 checkpoint 不同**：english 有 111 字符的静默窗口；multilingual 的告警与钳位**同时**到达（无静默窗口）。→ **「静默窗口」本身是一个逐 checkpoint 的可测量**，这比原表述精确得多。

### 1.5 计划器误差的直接测量（这是最干净的可测量）

同一状态、同一问题，**真实钳位字符数 vs 告警首次触发字符数**：

| checkpoint | 真实损坏起点 | 告警起点 | **未告警的受损区间** |
|---|---|---|---|
| english | 3083 字符 | 3194 字符 | **111 字符** |
| multilingual | ~3083–3194 字符 | 3194 字符 | ~0–111 字符 |

→ **这是「仪器自报不可信」的定量版本**，且**不依赖对 tokenizer 的估计**：只需扫字符数，读两个可观测量（`in_pad` 是否停在钳位、`truncated` 是否出现）。
→ **建议把它作为 M2 平面的主测量**（V3 的「尾部删除配对探针」作为交叉验证）。**这个测量 3 分钟内可完成，且逐 checkpoint 可复现。**

## 2. 裁决 V3 的其余指控

### 2.1 「3.2 ms/问」是 12× 乐观 —— **成立，且是设计级的**

V3：3.2 ms 是**同一 state 上 20 个问题**的摊销；而双平面回放**每个 state 只有一个问题**，因此**批大小被迫为 1**，正确数字是 **37.4 ms 墙体 / 30.0 ms 自报**。
**裁决：成立。** 我复核 R13 §8.2 的表：批 1 → 30.0 ms；批 20 → 3.2 ms/问。**回放平面的批大小是 1。**
→ **R5 §7 与 R3 §6 中的「3.2 ms」全部更正为 37.4 ms（墙体）/ 30.0 ms（自报）。** 这是论文自称「廉价」的那一项，**不能错 12 倍**。

### 2.2 A5b/A5c **没有 Laya 侧** —— **成立，且推翻我的 R5 裁决**

V3：**每个 Laya 入口都接受「一个 state + 一组问题」**，**没有跨 state 批处理**。因此
- A5b（8 个检查点窗口打进一次调用）= **对 Laya 不可构造**；
- A5c（同一问题 k=8 次独立采样）= **对 Laya 不可构造**，因为**答案是确定性的**（R13 §6.1 实测逐位相同）。

**裁决：成立。我在 R5 §3 冲突 1 的裁决（「保留 A5b/A5c 作为顺序往返匹配臂」）无法原样执行。**
**修复**：**效率主张改为「精确往返次数」的对比，而非「等预算前沿」**：
- LLM 判定器：**一次调用可判定 N 个检查点**（跨 state 批处理**可行**，因为每次调用是一个新的上下文）；
- 类型化判定器：**一次调用只能判定一个 state**，但**同一 state 上可打包 q 个问题**；
- → 因此**公平的对比是「每个检查点需要多少次顺序往返」**，并在**双方各自最优的打包方式**下测量。这是一个**更窄但可构造**的主张。

### 2.3 R15 的 `$3,802` 已定案：**100× 十进制滑移** —— **成立**

V3 定位到根因：`69,120 × $0.055`，即把声明的 `$0.00055/unit` **错写成 $0.055**（100×），且「5 judges」标签的乘数（5×120×576 = 345,600）**从未被应用**。
**裁决：确认算术错误，根因已定位。** 我的 R3 §3 独立复算（按其自身假设 ≈$38）与 V3 的 $38.02 吻合。**$3,802 作废。**
**另**：R15 的「115 h ÷ 8 流 ≈ 1.4 天」应为 **14.4 小时**（除法本身也错）。R5 §7 继承了两处错误 → **一并更正**。

### 2.4 Jev 126.81 ms 与 Laya 34 ms **不可并排** —— **成立**

V3：R3 §6 把 **Jev 第三方同机房 p50 126.81 ms** 与 **Laya 第一方本机 34 ms** 并排放；而 R13 实测**本机对 `api.typesafe.ai` 的未认证 403 拒绝**就要 **1,011–2,349 ms**。
**裁决：成立。** 两个数字**量的是不同东西、在不同机器上、一半还是拒绝而非推理**。
→ **R3 §6 的表必须拆分**：`本地第一方`、`远程第三方（标注来源与机房）`、`传输地板（拒绝）` **三行分列，禁止混排**。

### 2.5 V3 的一手测量（我采信，并调整成本模型）

V3 解码 12 份会话记录、185 步、`deepseek-flash @ max`：

| 项目 | V3 实测 | R15/R3 假设 |
|---|---|---|
| 解码速率 | 213.9 out-tok/s | — |
| 每步模型时间 | p50 **3,087 ms** / p90 **28,472 ms** | — |
| **输出** | **2,057 tok/步** | 900 → **低估 2.3×** |
| **缓存命中率** | **95.4%** | 85% → 低估 |
| `cacheWriteTokens` | **185/185 全为 0**（字段存在但为零） | 未考虑 |
| 推理 token 计数器 | **不存在**；`outputTokens` **包含推理** | 未考虑 |

**裁决：全部采信**（V3 是从真实记录解码的，且方法可复核）。三项后果：
1. **按可见文本估算输出会算错成本**——`outputTokens` 含推理，而推理在思考模式下默认开启。
2. **`cacheWriteTokens` 恒为 0 无法区分「免费」与「未记录」** → 成本表必须标注这一不确定性。
3. **缓存命中 95.4%** → 输入成本比我 R3 假设的更低，**进一步强化「钱不是约束」**。

### 2.6 成本重算与 **R3 §5 主张被推翻** —— **成立，且方向相反**

V3 自底向上重算：**计划 ≈$685（低谷）/ $1,370（高峰）**，而设计自称 $93。
→ **「钱不是约束」以约 20× 余量存活**（我同意）。
→ **但 R3 §5 的「Jev 成本优势随 horizon 消失」被其自身预算表反驳**：R3 的每一行都按**固定 1,500 token** 计价。**在 52k token 时，Jev 为 $150.9，而 LLM 判定器为 $68.6 —— Jev 贵 2.2×，符号相反。**

**裁决：R3 §5 的结论方向（优势消失）成立，但「交叉点 2,100–7,100 token」是静态假设下的产物；必须改为按每次运行实测的 state token 数逐点计价并画成 horizon 曲线。** 关键修正是：**Jev 的劣势比我说的来得更早、更大**，因为在长线上 state 会远超 1,500 token。

### 2.7 工期：机器时间不是瓶颈 —— **成立**

V3：机器时间 ≈ **23 h ≈ 1 天**（16 流），而非 R5 声称的 ~1.4 天@8 流；**总工期 5–9 周，其中机器时间占 4%**；**瓶颈是工程与分析**。
→ **并且三个证据支柱根本不需要生成电池**：截断曲线、confidence/高基数饱和、延迟+成本阶梯，**都可在合成 state 阶梯上测得**（约 800 次 Laya 调用 + 约 300 次串行 LLM 调用）。
→ **最小可行缩减**：保留 R15 的缩减电池（144 run × 60 步）**仅用于 T90/漂移** = **生成量减少 8×、机器 ~4 h、~$90、3–5 周**。

**裁决：接受。** 这是本次审计中**最有价值的可行性结论**：**论文的中心主张不需要昂贵的生成电池。**

### 2.8 校准的三个计划缺陷 —— **全部成立**

| # | 缺陷 | 后果 |
|---|---|---|
| a | **τ* 拟合与 ECE 报告无留出切分**（校准语料同时是 ECE 来源） | 泄漏 |
| b | **无分辨率下限** | **常数预测器**（按基率预测）**ECE ≈ 0 且分辨率 = 0**，会在纯 ECE 排行榜上**夺冠** |
| c | 校准语料只覆盖 **4 个任务族** | 任务族聚类自助法只有 **4 个簇**，两判定器 ECE 比较**永远达不到显著** |

**裁决：全部成立，尤以 (b) 最危险**——它会奖励一个什么都不学的判定器。
**修复**：① 留出切分（τ* 语料与 ECE 语料分离）；② **同时报告 ECE 与分辨率/判别度**，并明确声明纯 ECE 不可单独用于选型；③ 校准语料扩展任务族数（与 V4 的「族数是功效瓶颈」同一问题）。
**另**：**framing 绝不可合并**（同一 p 的 confidence 0.5399 vs 0.0046，差 117×）；**多语 `fitted_temperature_buckets: 0`（未校准）**；**english 的 `choice:11+ = 0.1006` 刻意破坏 k≥11 的校准** → **一个「总的 Laya ECE」毫无意义。**

### 2.9 缺失的推理档位扫描 —— **成立**

V3：R2 §A.1 把 `reasoningEffort` 称为**成本的主导变量**，而 R5 **从未扫描它**。
**裁决：成立。** `off / low / high / max` 是**成本与质量双轴的自变量**，必须纳入（≥100 次判定调用）。

## 3. 裁决 V4 的指控

### 3.1 **拨盘没有操纵 horizon** —— **成立，且是全文最严重的设计缺陷**

V4：`d = H − 4` **在所有层级上恒等**（R14 398–404 行）→ **「距污染距离」与「运行位置」完全共线**。而 §5.2 第 1 条使局部块在槽内 5 个层级**逐字节相同**，于是唯一变化的是**运出哪 5 行账本**。
两难（R14 未解决）：
- 若载体是**滚动尾部** → 决定性行在 H3/H4 已被滚出 → 这些条目被标 `absent` → §5.3 预注册的「只在 `survives` 条目上分析」在**最高两层为空** → G7 阻止漂移分析；
- 若**保留**毒化行 → `survives`≈100% → `absent` 对照为空 → **只剩新近性在变**。

→ **两种读法都无法隔离 horizon。**
**加剧**：300 条中 **170 条（57%）的答案只依赖局部块**（R14 自己说 Q4「local, short, shape-based」）；**真正活跃的条目只有 Q2+Q6+Q7 = 130/300**。

**裁决：成立。** 修复采用 V4 的方案，**且它成本极低**：
> **把 §4.3 已有的 `L` vs `L+C` 变体对提升为主分析**：**对全部 300 条各跑两个变体 = 600 配对观测**，每条多花一次判定调用。估计量变为 **carrier-lift × log2(H)**——**「痕迹是否存在」在条目内被操纵，混淆消除**。并**增加一个 `H4-refreshed` 单元**（长位置 + 新鲜痕迹）以打破共线。170 条惰性条目**作为干扰项安慰剂报告**。

### 3.2 可推导性 vs 不可回答性未识别 —— **成立**

V4：T3 的缓解**太弱**（提及标志是单边的，假阳/假阴未测；人工审计约 30/300 = 每层 6 条；载体升降探针 n=50）。
**更严重**：F3 的难度旋钮「(b) 源语义未定的列占比 0.10→0.60」是一个**不可回答性旋钮**——答案是作者的**私有参考变换**，从任何交付的字符串都**推不出来**；F4 的答案是在「脚本化参考策略」下的 argmax，其**最优性差距从未报告**。
→ **一个判定器无法从给定信息推出的答案，测的不是判定器。**
**修复**（V4）：在每族的 oracle 语言中建立**构建期蕴含 + 必要性证书**（蕴含证明可推导；必要性检测那 170 条惰性条目）；**可推导性上限检查**（用完整冻结日志的 LLM，在主 N 之外）；**把存活作为中介变量而非过滤器来分析**。

### 3.3 无有功效的推断归属 —— **其中一条对我的 R5 是致命的**

| 子项 | 内容 | 裁决 |
|---|---|---|
| (a) | R15 §5.1 **明文禁止** R14 的检验（「一切假设检验在 run 层或更粗；n 一律报 run 数与任务数，绝不报检查点数」），而 R14 的主分析是**条目层配对 McNemar** | **成立**——两单元直接冲突 |
| (b) | **n_eff**：5 条目/槽共享逐字节相同的局部块+答案，170 条对答案不敏感 → 惰性槽 ICC≈1 → **n_eff ≈ 77–106**，而 R14 需要 234；即便用 R15 自己的 DEFF=2.2 也只有 136 | **成立** → 所需原始 N = **515–700** |
| (c) | **R5 §5.5 的任务层随机化推断在算术上不可能显著**：最小双侧 p = 2/2^S → **4 族时 p ≥ 0.125**；R5 §5.1 的 3 族时 **p ≥ 0.25** | **成立且致命** |

→ **(c) 是我 R5 里的真实错误。** 任务层随机化推断在族数这么少时**无论花多少 N 都出不了 p<0.05**。
**修复**：随机化单位改为**运行谱系**（run lineage）且 **S ≥ 8**；或者**明确声明推断以这 4 个 authored 族为条件**（conditional inference），不再声称对族总体推断。R14 的「固定 x 剖面」设计**不**保护这一条。

### 3.4 V4 的两处**对简报前提的更正**（我采信）

1. **300 条对斜率是够的**——比 R14 自己论证的更好，原因 R14 从未说出：**每个槽携带完全相同的 x 剖面 {0,2,3,5,7}，因此槽随机截距对斜率方差的贡献恰好为零**；MDE ≈ **0.024–0.046 准确率/倍增**，满足预注册的 0.04–0.05 目标。
   → **但仅适用于槽内斜率**，一旦表达为 130 条活跃条目上的交互、或外推到 4 个 authored 族之外，**该优势消失**。
2. 因此 R5 §3 冲突 2 中「三个 N」的调和**方向正确但归属需改**：300 → 斜率；**≥515–700 → 边际对比**；≥1000 → 校准曲线。
